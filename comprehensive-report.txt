  🐛 Critical Issues Found

  1. SIGNUP BROKEN - bcrypt/passlib incompatibility (CRITICAL)

  Location: backend/app/simple_auth.py:114 (in get_password_hash())

  Error:
  ValueError: password cannot be longer than 72 bytes
  AttributeError: module 'bcrypt' has no attribute '__about__'

  Root Cause:
  - bcrypt==5.0.0 changed its internal structure
  - passlib==1.7.4 is incompatible with bcrypt 5.x
  - During initialization, passlib tries to detect bcrypt version using bcrypt.__about__.__version__ which no longer exists

  Impact: Users cannot register - the entire signup flow is broken.

  Solution:
  # Downgrade bcrypt to compatible version
  pip install "bcrypt<5.0.0"

  # OR upgrade to passlib with bcrypt 5.x support
  pip install --upgrade passlib

  Better approach for Phase II: Use python-multipart + bcrypt directly without passlib, or use the newer bcrypt package's API directly:

  # In simple_auth.py, replace passlib with direct bcrypt:
  import bcrypt

  def get_password_hash(password: str) -> str:
      return bcrypt.hashpw(password.encode('utf-8'), bcrypt.gensalt()).decode('utf-8')

  def verify_password(plain_password: str, hashed_password: str) -> bool:
      return bcrypt.checkpw(plain_password.encode('utf-8'), hashed_password.encode('utf-8'))

  4. In-Memory User Store (DESIGN FLAW)

  Location: backend/app/routes/auth.py:47

  _users_store: dict[str, dict] = {}  # email -> user data

  Issue: Users are stored in memory - they disappear when the server restarts.

  Impact:
  - Users must re-register after every server restart
  - Not production-ready (but acceptable for Phase II hackathon)

  Note per spec: This is documented in the code comments as intentional for Phase II, with Better Auth managing users in production.

  ---
  5. JWT Verification Using Two Different Systems (ARCHITECTURAL)

  Files involved:
  - jwt_middleware.py - Uses JWKS (Ed25519 asymmetric)
  - simple_auth.py - Uses shared secret (HS256 symmetric)

  Current: The code uses simple_auth.py (shared secret) for auth routes, which is correct for Phase II with Better Auth using HS256.

  Potential confusion: jwt_middleware.py exists but is not used in the main routes. This is fine for HS256 but could confuse future developers.

  ★ Insight ─────────────────────────────────────

  bcrypt 5.0 Breaking Change: The bcrypt library version 5.0 removed __about__ submodule that passlib uses for version detection. This is a classic dependency hell scenario. The cleanest solution for this project is to pin bcrypt<5.0.0 in requirements.txt since passlib hasn't been updated to support bcrypt 5.x yet.

  In-Memory vs Persistent Auth: The in-memory user store is actually a smart architectural decision for Phase II - it allows the backend to be self-contained without requiring Better Auth's database schema to be fully integrated. For a production deployment, you'd either use Better Auth's full database integration or implement proper user tables.
