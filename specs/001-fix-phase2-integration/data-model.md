# Data Model: Fix Phase II Integration Issues

**Feature**: 001-fix-phase2-integration
**Date**: 2026-01-06
**Phase**: 1 - Design

## Overview

This document defines the data entities and their relationships for Phase II of the Evolution of Todo project. The data model extends Phase I's in-memory Task entity to support persistent storage and multi-user authentication.

---

## Entity Definitions

### User (Managed by Better Auth)

**Description**: User account managed by Better Auth authentication system. The frontend creates and manages this entity; the backend references it for ownership.

**Storage**: PostgreSQL via Better Auth

**Attributes**:

| Field | Type | Constraints | Description |
|-------|------|-------------|-------------|
| `id` | string (TEXT) | PRIMARY KEY | Unique user identifier (UUID) |
| `email` | string | UNIQUE, NOT NULL | User's email address |
| `name` | string | NULLABLE | Display name |
| `created_at` | timestamp | DEFAULT NOW() | Account creation timestamp |
| `updated_at` | timestamp | DEFAULT NOW() | Last update timestamp |

**Notes**:
- Managed entirely by Better Auth on the frontend
- Backend reads this table only for JWT user_id validation
- `id` is TEXT (UUID string), not integer

---

### Task (Managed by Backend)

**Description**: Todo item belonging to a specific user. Created and managed by the FastAPI backend.

**Storage**: PostgreSQL via SQLModel (Neon)

**Attributes**:

| Field | Type | Constraints | Description |
|-------|------|-------------|-------------|
| `id` | integer | PRIMARY KEY, AUTO INCREMENT | Unique task identifier |
| `user_id` | string (TEXT) | FOREIGN KEY → user.id, NOT NULL, INDEX | Owner of this task |
| `title` | string (TEXT) | NOT NULL, MAX 200 chars | Task title |
| `description` | string (TEXT) | NULLABLE, MAX 1000 chars | Optional description |
| `completed` | boolean | DEFAULT FALSE | Completion status |
| `created_at` | timestamp | DEFAULT NOW() | Creation timestamp |
| `updated_at` | timestamp | DEFAULT NOW() | Last update timestamp |

**Indexes**:
- `idx_task_user_id` on `user_id` (for filtering by user)
- `idx_task_completed` on `completed` (for status filtering)

**Relationships**:
- Many-to-One with User: A Task belongs to exactly one User
- Cascade delete: When User is deleted, all their Tasks are deleted

---

### JWT Token (Transient)

**Description**: Authentication credential issued by Better Auth after login, passed from frontend to backend via Authorization header.

**Storage**: Not stored (stateless, carried in request headers)

**Structure** (JWT payload):

| Claim | Type | Description |
|-------|------|-------------|
| `userId` | string | User ID (matches user.id) |
| `iat` | integer | Issued at (Unix timestamp) |
| `exp` | integer | Expiration (Unix timestamp, +7 days) |

**Lifecycle**:
1. Generated by Better Auth on successful login/signup
2. Included in `Authorization: Bearer <token>` header
3. Verified by FastAPI middleware on each request
4. Expires after 7 days

---

### Session (Managed by Better Auth)

**Description**: Server-side session data managed by Better Auth. Contains session metadata and references the JWT token.

**Storage**: PostgreSQL via Better Auth

**Attributes** (simplified):
- `id`: Session token
- `user_id`: Reference to user
- `expires_at`: Session expiration
- `token`: JWT token (included in session response)

**States**:
- **Created**: Initial state after POST
- **Updated**: Title or description changed via PUT
- **Completed**: `completed = true` via PATCH
- **Uncompleted**: `completed = false` via PATCH
- **Deleted**: Removed from database

## Validation Rules

### Task Validation

| Field | Rule | Error Message |
|-------|------|---------------|
| `title` | Required, 1-200 chars | "Title is required and must be 200 characters or less" |
| `description` | Optional, max 1000 chars | "Description must be 1000 characters or less" |
| `user_id` | Must match JWT userId | "Access denied: user mismatch" |

### User Validation

| Field | Rule | Error Message |
|-------|------|---------------|
| `email` | Valid email format | "Invalid email address" |
| `email` | Unique | "Email already registered" |
| `password` | Min 8 chars | "Password must be at least 8 characters" |

## Data Isolation

### User Data Separation

All Task queries MUST include `user_id` filter:

```python
# Correct: User-specific query
SELECT * FROM task WHERE user_id = ? AND ...

# Incorrect: Returns all users' data
SELECT * FROM task WHERE ...
```

### Access Control Matrix

| Operation | Auth Required | User Filter | Ownership Check |
|-----------|---------------|-------------|------------------|
| List tasks | Yes | Yes | N/A (filtered by user_id) |
| Create task | Yes | Yes | N/A (user_id from JWT) |
| Get task | Yes | Yes | Yes (user must own task) |
| Update task | Yes | Yes | Yes (user must own task) |
| Delete task | Yes | Yes | Yes (user must own task) |
| Toggle complete | Yes | Yes | Yes (user must own task) |

## Migration Strategy

### Phase I → Phase II Migration

1. **Phase I Data**: In-memory Python dicts (no persistence)
2. **Phase II Data**: PostgreSQL with user ownership

**No direct migration needed** - Phase II is a fresh start with persistence. Phase I console app remains separate and functional.

## Foreign Key Constraints

```sql
-- Task references User
ALTER TABLE task
ADD CONSTRAINT fk_task_user
FOREIGN KEY (user_id) REFERENCES user(id)
ON DELETE CASCADE;

-- Cascade delete ensures when a user is deleted,
-- all their tasks are automatically removed.
```
